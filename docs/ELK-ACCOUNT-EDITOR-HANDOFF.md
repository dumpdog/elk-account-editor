## Goal
Build a tool that creates a new Elk M1G account from a template by **editing an ElkRP "Export Account" file** (not the database). The edited file is loaded in ElkRP with **File > Import Account**. This is a stepping stone toward porting ElkRP to Apple Silicon. **Only M1G panels matter.** One single-record write test has been done on a spare test panel (see Live panel below); nothing else has ever been written to a panel.

## Export file format (VB `Write#`)
One value per line, CRLF, strings quoted, numbers plain. Line 1 is the quoted 25-field account header (field 1 account id, 17 panel type, 18 software version, e.g. "5.0.12"). Each section is found by shape; every other line is copied through unchanged, so an unedited open/save is byte-identical (tested).

Section order: Account details, Users, Areas, Keypads, Zones, Wireless, Globals, DawnAndDusk, Telephones, ..., Report Codes (communicator).

| Section | Layout | Notes |
|---|---|---|
| Users | count, N x (number, 28 bytes) | codes: bytes 0-5 digits reversed; flags byte 6 (bit7 Arm, 6 Disarm, 5 Bypass, 4 Access, 2 Master, 1 Menus1-5), byte 7 bit0 Duress, byte 8 area bits, bytes 9-24 name, byte 25 bit7 temporary. Code length 4 or 6 from Globals byte 0 bit 2 (first Globals value is at zonesEnd+780). |
| Areas | count, N x (number, 24 bytes) | name 0-15, exit1 16, entrance1 17, exit2 18, entrance2 19, flags 20/21, arm window 22 |
| Keypads | count, N x (number, 148 bytes), then 16 keypad-version values | area byte 0, name 6-21, F-key defs 28+2f, F-key names 52+16f |
| Zones | count, N x (number, 32 bytes), then 13 wireless-group flags (sw >= 5) | function, flag1, flag2, unused, name[16], 6 voice words. Entries are sparse and ascending. flag1: Bypassable 0, PeriodicTrip 1, FastLoop 2, ForceArm 3, Chime 4, CrossZone 5, DialerDelay 6, ListenIn 7. flag2: type bits 0-2 (hookup 0-6), swinger bit 3, area bits 4-6 (area-1), silent bit 7. |
| Wireless | 3 x 260 values (sw >= 5) | per-device data, **not edited** |
| Telephones | count, N x (id, 88 bytes) | exact position = zonesEnd + 780 wireless + Globals (48 values if sw string starts above "4.3", else 36) + Dawn/Dusk 102. Count may be 0 (e.g. TESTINGRHTEST, sw 5.3.44). Shape search is only a fallback |
| Report codes | area RCs, user RCs, zone RCs, system, keypad (see below) | found by shape search after the telephones |

Default zone voice: "Zone" (471), then One/Two (22/23) for 100-299 plus Hundred (49) if remainder < 10, then teens/tens/ones words. Verified against 912 stored default zones. New zones get it automatically.

### Wireless zone groups (Elk rules, from the user)
- Group g = zones 16(g-1)+1..16g, 13 flags.
- Wireless rule (installation manual, quoted by the user 2026-11-10): the primary wireless transceiver is enrolled at data bus address 2 and the first wireless zone is always zone 17; no wireless zone may exist beyond zone 160 (a full 144 = groups 2-10); each hardwired expander enrolled in zones 33-160 uses up one wireless group of 16. So the editor refuses only group 1 and groups past zone 160, and allows gaps. Earlier versions required an unbroken run from group 2, which rejected an ElkRP export that has only group 3 on.
- The number of groups is independent of the transceiver count. One receiver serves up to 144 zones (9 groups). At most 3 transceivers can be added; they only extend range.
- Editor: "Wireless zone groups" selector (None..12). A warning shows above 9 groups (not blocked). `AccountModel.ValidateWirelessGroups` refuses saves that break the rule. Changing the count does NOT renumber existing zones.

### Telephones (88-byte record)
- Number ASCII 0-19; flags byte 20 (bit7 area events, 6 zone bypass, 5 zone trouble, 4 user events, 3 global); byte 21 high nibble = reporting format; byte 22 = attempts; 8 x 6-char ASCII account numbers at 23-70 (one per area); name 71-86.
- Format: 0 Disabled, 1 Contact ID, 2 SIA FSK, 3 Pulsed 4+2, 4 DTMF Pager, 5 Voice Message, 6 IP, 7 Serial Expander (7 only on sw >= 4.3.6). Saving refuses > 7.
- IP format (6): attempts forced to 1 at most (verified against ElkRP export). IP area tick state is **not stored separately**: ElkRP ticks an area when its account number is above zero (`Val(AccountCode_n.Text) > 0` on load) and the checkbox just writes `009999` (ticked) or `000000` (unticked) into that area's account box (`EtherArea_CheckedChanged`, `Telephone_Numbers.cs`). So `Sample Import F2 Com` (area 1 `123456`, others `000000`) means area 1 ticked only. Switching format does not change the numbers. The editor shows IP area checkboxes on that basis (tick = non-zero; ticking writes 009999).
- Phone entries can be added in the editor (ids 1-8).

### Communicator / report codes (`Report_Codes.Form_Export`)
File order: `mNumAreaRCs`, N x (area number + 20 bytes); `mNumUserRCs`, N x (user number + 4 bytes); `mNumZoneRCs`, N x (zone number + 4 bytes); 24 system bytes; 96 keypad bytes (16 keypads x 6 F-keys).
- Area bytes: 0 abort time, 1 cancel time, then 17 codes (2-18): Abort, Cancel, Auto close, Early close, Closing extended, Fail to close, Late close, Key switch close, Duress, Exception open, Early open, Fail to open, Late open, Key switch open, Keypad lockout, Exit error, Fail to communicate; byte 19 unused.
- User bytes: Close, Open, 2 unused. Zone bytes: Alarm, Restoral, Bypass, Trouble.
- System bytes: 0 AC fail delay, 1 test hours, 2 test minutes, 3 test days, then 18 codes (4-21): AC fail, AC restore, Auto test, Aux over-current, Aux over-current restore, Expansion module trouble, Expansion module restore, Installer on premises, Installer off premises, Log 80% full, Low battery, Low battery restore, Memory error, Remote programming end, Phone line fault, Phone line restore, Output 2 fault, Output 2 restore; 22-23 unused.
- Report code values (from the user): `00` off, `01` new events and opens, `03` restorals and closings (Contact ID prefix 1 or 3). Editor shows checkboxes; ticking writes 01 or 03 by event.
- 03 events: area Auto close, Early close, Fail to close, Late close, Key switch close; user Close; zone Restoral; system AC restore, Aux over-current restore, Expansion module restore, Low battery restore, Phone line restore, Output 2 restore, **Installer off premises (a guess)**. Remote programming end is left at 01 (also unconfirmed). Everything else 01.
- Values already in the file that are not 00/01/03 are kept until that box is changed. Button "Set the ones that are on to the standard 01 / 03" normalises. `Sample Communicator` has all area codes at 01 (closings should be 03 per the rule).
- Keypad RCs: only keypad 1 F1-F3 are on in the sample (F4-F6 left 00).

## Standalone desktop app (added 2026-11-09)
- The editor now runs in its own native window, no browser needed. It still hosts the same web page, served from a loopback-only server, inside the system web view via Photino.NET 4.0.16 (WebView2 on Windows, WebKit on macOS). Window code: src/Elk.Editor/NativeWindow.cs; start-up in Program.cs.
- Run `ElkAccountEditor.exe [export file]`. `--browser` opens a browser tab instead (the old behaviour). If the native window cannot start, it falls back to the browser by itself.

- Open and Save use the operating system's file dialogs through the window bridge (window.external.sendMessage / receiveMessage: commands openFile, saveFile). The Photino save dialog takes a start folder, not a file name, so the suggested name is shown in the dialog title. In a browser the old file input and download are used.
- The server now prefers fixed port 51980 (falls back to any free port) so drafts and the remembered panel address in the page's local storage survive restarts.
- Tested on Windows: published single-file exe opens its own window and loads the editor; native Open loaded a chosen file; native Save wrote a file byte-identical to the original for an unedited save; closing the window ends the process and server. Page-level checks were driven through the WebView2 debug port (set WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222; scratchpad cdp.js is a small CDP driver).
- macOS: builds (osx-arm64) as ElkAccountEditor plus Photino.Native.dylib, which must stay in the same folder. NOT yet run on a Mac. The user plans to wait and may use Xcode (WKWebView) instead; Photino's WebKit window and its open/save dialogs are untested. `--browser` is the fallback and was verified on the Mac earlier (browser version).

## Deleting records (added 2026-11-09)
- Not every panel has 208 zones, 199 users and so on. The editor can now delete: **zones** (tick rows then Delete ticked zones, or type N and "Keep only zones 1 to N" to drop everything above N), **users** (tick and delete; user 1 and the special 200+ codes are protected), **areas** (Delete on the card; refused while zones or keypads still use the area), **keypads** and **telephones** (Delete button per row). All use a two-click confirmation and are undoable.
- Mechanism: the page sets MODEL.prune = true; AccountModel.ApplyTo then removes file entries that are not in the model (zones, users, areas, keypads, phones and their report-code rows; a deleted keypad's six keypad report bytes are zeroed). Without Prune nothing is ever deleted, so older flows are unchanged. Guards: at least one area, one keypad and user 1; deleting an area that zones/keypads still point at is refused.
- Panel side: a record that is not in the file is normally left alone on the panel. The Panel dialog has "Also reset records on the panel that are not in this file to factory defaults" (PanelRequest.ResetMissing / CLI `upload-export --reset-missing`): zones 1-208, users 2+, areas 2+, keypads 2+, telephones, area/user/zone report codes that the file lacks are compared with DefaultRecords (Elk.Protocol/DefaultRecords.cs) and written when different, shown in the diff as "zone (reset)" etc. User 1, area 1 and keypad 1 are never reset.
- DefaultRecords were checked byte for byte against an untouched factory-default panel: 206 of 208 zones match (zone 17 and 186 are all-zero on that panel), plus user 100, area 5, keypad, phone and report-code defaults. Unit tests: DeleteTests, PanelResetTests.
- Tested in the app: Keep only zones 1 to 16 on a 48-zone account (armed label, deleted 32, saved file 1,056 lines shorter, reopened with 16 zones), Undo/Redo restores both the zones and the prune flag; Compare with reset against the live panel listed only genuine differences. Deleting areas/users/keypads/phones in the page UI was not driven in the app (covered by unit tests on the model).
- Note: the spare panel is no longer in its original state; the user sent changes from the Mac (zones 17-48 etc.). Backups of the original state: TESTING\LIVE\full-download.ORIGINAL.json (and the ones in Documents\ElkEditor backups).

## Globals editing (added 2026-11-10)
- New **Globals** tab (index.html globalsTab). Byte/bit positions come from ElkRP's Globals form (decompiled Globals_Data.cs, PopulateScreen): byte 0 bits 7/6/5/4 clock, date, temperature, DST; bit 3 audible troubles; bit 2 code length (read-only here); bit 0 cross-zone verify; byte 1 verify time; bytes 2/3 fast/slow loop (x10 ms); byte 4 rings (high nibble) and two-way volume (low 3 bits); byte 5 areas 2-8 common to area 1; bytes 6/7 output 1 volumes; byte 8 output 2 delay; byte 9 voice message flags and output 2 hookup (bit 7); byte 10 two-way callback; byte 14 bit 0 wireless jam detect; byte 15 CS verify time; byte 16 wrong-code lock-out; byte 28 UPB; byte 29 line-fault timer (low 5 bits), ring/hang-up (bit 5), telephone control (bits 6-7); byte 30 serial text flags and Menus 1-5 code (bit 7); byte 35 baud (low nibble), two-way listen-in (bit 4), keypad keys (bit 5).
- Also editable (second pass): **user code length** (flips byte 0 bit 2 like ElkRP, and re-reads every user code at the new length: 4 to 6 pads two leading zeros, 6 to 4 keeps the last four), **daylight-saving start/end** (DST1 = month x 16 + weekday 1-7 Sunday-Saturday, bit 3 set means fixed date; DST2 = 1/8/15 for first/second/third, ElkRP's per-month day number for "last" (25,22,25,24,25,24,25,25,24,25,24,25), or the day of month for a fixed date), **local (keypad) programming code** (bytes 22..17 hold the 6 digits first to last), and **country** (byte 47) plus the 11 modem values (36-46) as raw numbers. ElkRP fills the modem values from a country table in its own database that is not available here, so changing the country alone does not change them. Anti-takeover lockout is not in the export file or the 48-byte block, so it is not covered.
- Model: AccountModel.Globals (int[], edited in place; ApplyTo calls AccountFile.SetGlobals only when changed, so untouched files stay byte-identical).
- Panel: DiffAsync/ApplyAsync include globals (section 7 item 1), including country and modem values. The local (keypad) programming code (bytes 17-22) is only sent when asked for: Panel dialog tick box, PanelRequest.SendLocalCode, CLI `--send-local-code`; otherwise the panel keeps its own, so a file (for example a blank template) cannot lock RP out. Tests: GlobalsTests. **Live test 2026-11-10 (not the RP code):** pulled the panel into an account (compare = 0 changes), changed Two-Way Callback Time (byte 10) by 1, compare = exactly 1 change (globals), send wrote 1 and the read-back differed in 0, a fresh pull showed the new value, then reverted the same way; the final globals equal the original byte for byte (backup before: TESTING\ROUND6\before-globals.json). **Sending a changed local programming code is untested on hardware.**
- Verified in the app: Globals tab renders 10 cards, edits change MODEL.globals, Save produces a file.

## Wireless devices (added 2026-11-10)
- New **Wireless devices** tab. File layout (software 5.x): three 260-value blocks straight after the zone group trailer (ElkRP writes WZNBytes, WZNBytes1, WZNBytes2). Block b covers 48 zones starting at (block 0 byte 2 & 0xF8) + 1 + 48b (start zone 17 when byte 2 = 16). Per slot s in a block: byte 4+s = flags (bit 0 enabled, bits 1-2 supervision 0 none / 1 normal / 3 fire, bit 3 option 1, bit 4 option 2, bit 5 PIR, bits 6-7 hardwired loop); byte 52+s = key fob user number (199 on every slot in the test files); bytes 116+3s..+2 = transmitter ID (3 bytes; ElkRP shows 7 hex digits with a leading 0); bytes 0 and 1 of block 0 = non-fire and fire supervision windows; bytes 114-115 = event number (not edited, bytes 100-115 are kept as they are).
- Verified against real ElkRP exports: R5-B Wireless (zones 33-36: door contact, motion, heat, key fob) decodes to the expected options (heat = fire supervision, serials 0000033-0000035), and R7-B (zone 33 changed from option 1 to option 2) differs from it in exactly that one flag byte (41 -> 49). Test: WirelessTests (real-file checks skip when TESTING is absent).
- Panel: wireless is section 15 and **the part selects the block (0-2); the item number is ignored (the panel mirrors it)**. Writing "item 1, 2 or 3" with part 0 hits the same block, which is why the first live attempt showed three blocks changing. PanelSync, the pull and the backup (BlockJson.Part) all use parts now. Older backups have no wireless blocks.
- Live test on the spare panel (no wireless receiver): pulled, compare = 0 changes, flipped one flag of an unused slot, compare = exactly 1 change, send wrote 1 with 0 left on read-back, reverted the same way, final blocks identical to the original.
- The wireless group rule was relaxed on 2026-11-10 (see Wireless rule above), so the R5-B Wireless export (group 3 only) is valid.
- Not done for wireless: editing the start zone, receiver mode bits (block 0 byte 2 low bits) and the event number; enrolling real devices was not tested (no receiver).

It is NOT the RP access code, which is what ElkRP and this editor use to connect (factory default 246801) and which is not part of the globals. The tick box still defaults to off, so a file never changes the panel's keypad programming code unless asked.

- Undo/redo keep up to 200 steps (typing within 0.7 s counts as one step). New **History** button next to Redo lists the recent changes, newest first, described from the data ("Zone 4: name", "Globals: wrong code lock-out", "Wireless zone 33: device options"); clicking one goes back to just before it, and the entries above "Current state" redo. ## Live status and a connection that stays open (added 2026-11-10)
- **Status (live)** tab, modelled on ElkRP's "Current Status and Remote Control" window (decompiled RemoteControl.cs). Read only; no arm, disarm or bypass buttons were added. Four queries, all `7F 00 00 n` on an open session: n = 6 areas (68 byte reply), 7 system alarms and troubles (56), 8 zones (212), 16 zone voltages (212). Decoding is in Elk.Protocol/PanelLive.cs: area n state byte = reply[8n] (bits 0-1 = 3 alarm; bits 2-4 = 0 not ready, 4 ready, 8 ready to force arm; bits 5-7 = armed level 0 disarmed, 1 away, 2 stay, 3 stay instant, 4 night, 5 night instant, 6 vacation); zone n byte = reply[n+3] (bits 0-1 physical: 0 N/A, 1 open, 2 EOLR, 3 short; bits 2-3 logical: 0 normal, 1 trouble, 2-3 violated; 0x20 bypassed; 0x10 force armed); voltage = reply[n+3] / 10; each non-zero byte of reply[4..55] names an entry of PanelLive.SystemNames (fire, medical, police, burglar, AC failure, low battery, telephone fault, ...).
- Server: Elk.Editor/LivePanel.cs keeps one session open. `/api/live/connect`, `/api/live/disconnect`, `/api/live/status` (polls the panel). While it is open, compare / send / read / backup / restore borrow the same session (the M1XEP allows only one connection, so they would otherwise be refused); a broken connection is closed and reported. The page polls every 2 s while connected, which also keeps the session alive.
- Verified on the spare panel: connect, firmware and serial shown, areas (area 1 not ready, 2-8 ready, all disarmed), zones 1-16 violated/open at 13.6-13.7 V (unwired inputs), no system troubles; a Compare ran on the same open connection (no second login) while polling continued. Tests: LiveTests (decode checks use values seen on the real panel; simulator answers the status queries).
- **Remote control** (PanelControl.cs, ElkSession.ReceiveAnyAsync, `/api/live/control`, CLI `status` and `control`): zone bypass toggle `FF 00 00 09 00 zone area 00`, arm or disarm `7F 00 40 00 area level` (0 disarm, 1 away, 2 stay, 3 stay instant, 4 night, 5 night instant, 6 vacation), silence and reset `FF 00 00 0A area`. The panel sends no reply to any of them; the status read afterwards shows the result. In the Status tab every control needs a second click to confirm. Verified on the spare panel with both the CLI and the page: zone 1 bypassed and un-bypassed, area 2 armed Stay and disarmed; the panel finished unchanged. Silence/reset was not exercised (no alarm to silence), and arming an area with open zones was not tried.
- Not done: output and task status, and the other live pages ElkRP has.

## The secure port is TLS, not the AES passphrase (found 2026-11-10)
- The M1XEP's secure port (2601) is a **TLS** connection (ElkRP ConnectMethod 50, decompiled TLS.cs: SslStream, TLS 1.2, host name "M1XEP"). ElkRP accepts the module's self-signed certificate when its issuer is "CN=M1XEP, OU=Engineering, O=Elk, L=Hildebran, S=NC, C=US" (or "CN=HTTPS Certificate"). There is **no passphrase, user name or password**; the M1XEP web page user names and passwords are unrelated. The earlier attempts with the AES scheme (ConnectMethod 51: key = AES-ECB of the passphrase with the MAC as key) failed because that scheme is not what this module speaks.
- Inside the TLS stream the protocol is the same framing as the non-secure port. The login is `7F 00 00 01` + the six access-code digits (last first) + the 16-byte identity block (AES-128-CBC, zero IV, fixed ElkRP key, over: random byte, the control's 8 serial-number hex digits, random byte, the six code digits), see Handshake.IdentityBlock and ConnectMode.Tls. The only extra input is therefore the **panel serial number** (8 hex digits, on the control board and in ElkRP's account details; the replies also report it).
- Implemented: ElkSession.Tls(serial) (Stream is now a plain Stream, SslStream when TLS), PanelConnection.Settings(Tls, Serial), CLI `--tls --serial 00000001 --port 2601`, and in the editor the Connection choice "Secure port, TLS" with a serial field (Panel dialog and Status tab). The AES option stays as "Secure port, AES with passphrase (older)" for modules that use it; it is untested on hardware.
- Verified on the spare panel: CLI `status` over TLS, then in the editor a live connection and a full backup (208 zones, 629 blocks) on one open TLS connection. No packet capture was needed.
- Not tested: TLS 1.0/1.1 modules (older M1XEP firmware; ElkRP falls back to the OS default there, this code only offers TLS 1.2), and certificates with other issuers (they are refused with the handshake error shown).

## Module enrollment and the installed-device list (added 2026-11-10)
- New **Modules** tab (needs the live connection from the Status tab), from ElkRP's "Enroll/Update Control and Devices" window (decompiled SystemVers.cs). It lists the control, every module enrolled on the data bus and the M1XEP with model, hardware, boot and firmware versions, and has an **Enroll bus modules** button (two clicks) that does what Bus Module Enrollment (installer menu 01) does at a keypad.
- Protocol (Elk.Protocol/PanelModules.cs): Enroll = `7F 00 00 11`; the panel answers with a bare ACK frame (`10 06`, shown by ElkSession.ReceiveAnyFrameAsync) and rescans the bus; ElkRP then waits about 10 seconds and logs in again, the editor waits 12 s, checks the session and reconnects if the panel dropped it. Enrolled devices = the bitmaps in the reply to `7F 00 00 04` (ElkRP's ValidItems table: 32 devices per group, highest byte first; group 0 keypads 1-16, group 1 input expanders 1-13, group 2 output expanders 1-13, group 4 serial port expanders 1-7; the first byte of group 0 is reply[num+4] with num = 47 / 59 / 147 / 151 for reply lengths up to 76 / 88 / 171 / more). Versions: `7C 00 type address` (type 1 keypad, 2 input expander, 3 output expander, 5 serial expander; reply hardware [8..9], boot [10..12], firmware [13..15]; firmware FFFFFF = missing, 0 = erased) and `75 06` for the M1XEP. Models come from the hardware number (keypads: 0 M1KP, 1 M1KP2/KP3, 2 M1KPAS, 3 M1KAM, 4 M1KPNAV, 5 P212S; input expanders: 0 M1XIN, 1 M1XRF2G, 2 M1XRF1N, 3 M1XRF2N, 4 M1XRF2H, 5 M1XRFEG, 6 M1XRFTW, 7 M1XRFTWM, 8 M1XRF319, 9 M1XRF2Hv2; output expander M1XOV(R); serial 10 M1XSLU, 11 M1XSLZW, else M1XSP).
- Verified on the spare panel (over the secure TLS port): Control M1G hardware 0.13 / boot 3.3.6 / firmware 5.3.44, Keypad 1 M1KP2/KP3 hardware 1.6 / boot 1.0.14 / firmware 1.0.20, M1XEP hardware 1.0 / boot 2.0.4 / firmware 2.0.51. Enroll was run three times (CLI and the page): the panel acknowledged it and the list was the same afterwards, as expected with both modules present. **Verified by the user, 2026-11-12:** Enroll bus modules scanned the bus and then listed a newly added M1XIN input expander; after that module was removed, the list showed it as "Missing or not working". Still not tested: other expander types, serial port expanders, and the version query for the old M1XIP (type 8). CLI: `modules` (read only) and `enroll --yes`.
- Warning in the UI and docs: modules that are enrolled but not answering during enrollment are dropped.

## The Live tab: status, event log, modules, time and date, RP access code (added 2026-11-12)
- The old **Status (live)** and **Modules** tabs are now one **Live** tab: the connect form on top, then Status | Event log | Modules | Time and date | RP access code (page code liveTab / statusView / logView / timeView / codeView; modulesTab is reused). A lost connection redraws the whole tab (Connect form back, message "Disconnected.").
- **Time and date** (Elk.Protocol/PanelClockLog.cs, from ElkRP SetTime.cs): read = `7F 00 00 03`, reply bytes 4..10 = second, minute, hour (BCD), day of week (Sunday = 1), day, month, year-2000 (BCD); set = `FF 00 00 03` + the same 7 bytes, panel answers ACK. Buttons: set to this computer's time, or to a chosen time (both two-click). Endpoints /api/live/time and /api/live/settime.
- **RP access code** (PanelAccess, from the Change button in ElkRP's account details, Account_Details.cs btnChangeRPCode_Click): `7F 00 00 05` + the six digits, last digit first (same order as the login), panel answers ACK. Only changes anything once the panel acknowledges; then the editor remembers the new code for reconnects. Two entries must match, two clicks. **Not tried on the real panel** (a wrong write could lock the spare panel out of ElkRP); only checked against the simulated panel and ElkRP's code. Endpoint /api/live/accesscode.
- **Event log** (PanelLog, from ElkRP ReceiveLog.cs; **verified on the real panel 2026-11-16**): request `7B 14 hi lo` (20 entries, from address 65535 = newest); reply [1] = count, [2..3] = next address (descending by 20, the log is a ring of 512 slots), 8 bytes per entry from [4]. Entry bit layout (from AddLogLine): year-2000 (5 bits), month 4, day 5, hour 5, minute 6, day of week 3, area-1 3, event number 12, item-1 9, then 3 bits. An all-zero entry ends the list. **Event 4095 is an END OF LOG marker the panel writes into the log when it gets ElkRP's opening request `7B 00 00 00`** (stamped with the time, it then sits between the newer and older events); the editor does not send that request (it would add a marker to the log on every read; three were added to the spare panel while this was worked out) and skips any marker it finds. One lap = 512 slots, then it stops. Seen on the spare panel: 1363/1364 around every login and logout, 1388/1389 when the clock is set, 1173/1174 for area 2 (the Nov 11 arm/disarm tests), 1239 (items 1-16) and 1240 (items 1-5) in bursts from bus module enrollment. Only events 1-36 are named (zone definitions, as ElkRP does); the rest show as "Event N" until ElkRP's event table is available. Endpoint /api/live/log?max=.
- **Time and date verified on the real panel**: the panel clock was 1 h 45 min ahead of the PC; "Set to this computer's time" was acknowledged and the panel then read the PC's time.
- Simulated panel (tests) now answers clock read and set, access code change (ACK) and the log; FrameParser has an option so the simulator can parse PC-to-panel frames that start with 0xFF (the PC-side parser treats a 0xFF body as debug text). 7 new tests (ClockLogTests), 122 in all.
- **Panel dialog**: the "also send the local keypad programming code" tick is gone (the panel keeps its own bytes 17-22; the API field stays, false). ## Gotchas learned
- Jet (`.mdb`) only works from 32-bit PowerShell (SysWOW64). No Python installed (use node, C#, awk).
- ElkRP pads text with NUL or space; the apply code rewrites a text field only when its visible text changed, which keeps unedited round-trips byte-identical.
- Editing `index.html` with scripted replacements once deleted the Communicator code by mistake; always run `node --check` on the extracted `<script>` and open the page after edits.
- Close the running editor before republishing the Windows exe.
